# Surface: Product and POC Architecture

Status: working product thesis and proof-of-concept specification\
Version: 0.1\
Date: 2026-08-29

## 1. Product thesis

Surface is an agent-native UI language and compiler with React as its first
rendering backend.

> AI writes it. Humans use it. Other AI can read and operate it.

The product is not primarily another collection of React buttons and cards. It
is a semantic contract from which several representations are projected:

- Beautiful human UI
- Semantic HTML and an accessible browser tree
- Structured JSON containing raw values, entities, state, and actions
- Fetch-friendly Markdown
- Agent-callable actions through future WebMCP, MCP, or API adapters
- Executable requirement and behavior checks

The core invariant is:

> Human and agent representations are projections of the same bound semantic
> surface and action registry. No projection independently redefines values,
> action identity, input schema, availability, confirmation policy, or dispatch.

## 2. Why this product exists

Current projects solve parts of the problem:

- React Aria and Radix provide accessible interaction primitives.
- shadcn/ui distributes polished, customizable component source.
- CopilotKit colocates some tool schemas, actions, and renderers.
- A2UI defines a catalog-driven protocol for agent-generated interfaces.
- MCP Apps transports interactive tool UIs to agent hosts.
- WebMCP proposes browser-native, in-page tools for browser agents.

The unmet opportunity is the closed semantic loop:

```text
Human states intent
        ↓
Agent authors a constrained interface
        ↓
Compiler renders a coherent human experience
        ↓
Another agent recovers the same meaning from the URL
        ↓
Human and agent actions use the same command binding
```

The differentiation is not simply “output JSON.” It is semantic parity,
component selection by task fit, compiler-enforced invariants, and measurable
authoring and consumption reliability.

## 3. Product principles

### 3.1 Humans author intent

Humans describe:

- Audience
- Outcome or goal
- Important information
- Available tasks and decisions
- Priority and hierarchy
- Safety requirements
- Responsive or platform constraints
- Acceptance scenarios

Humans should not need to know component names, JSX, CSS, or layout APIs.

### 3.2 Agents author surfaces

Agents select semantic components, bind known data, bind registered actions, and
explain their choices. They do not generate arbitrary JSX or CSS.

### 3.3 Constraints produce quality

The agent chooses meaning and limited presentation intent. The design system
chooses typography, spacing, focus behavior, responsiveness, animation, and
visual polish. Constrained design grammar is more reliable than generated
utility-class strings.

### 3.4 React is a renderer, not the language

The canonical machine artifact is a versioned `SurfaceSpec`. React is the first
renderer, but semantics are not encoded only in React implementation details.

### 3.5 Agent readability is progressive enhancement

The universal baseline is server-rendered semantic HTML. Structured JSON,
Markdown, and tool adapters supplement rather than replace it.

### 3.6 Machine-readable is not automatically safe to operate

The UI contract can describe and initiate actions. Backend commands must still
enforce authentication, authorization, validation, idempotency, auditability,
and transaction policy.

## 4. Authoring model

### 4.1 Progressive precision

Surface accepts four conceptual input levels:

1. Natural-language brief
2. Natural language with acceptance scenarios
3. Optional structured Intent Markdown
4. Direct machine-authored `IntentSpec` or `SurfaceSpec`

The human-facing DSL is optional. Its primary role is a reviewable intermediate
contract generated by the agent, not a language humans must learn.

### 4.2 Intent Markdown

An effective brief looks like:

```md
# Refund review

## Audience

Support leads

## Goal

Decide whether an escalated refund should be approved.

## Requirements

- Show refund amount, reason, and order status.
- Show previous refunds chronologically.
- Make fraud warnings prominent.
- Approving is primary.
- Denying requires confirmation.
- Mobile is review-only.

## Scenarios

Given a pending refund and an authorized lead When the lead denies the refund
Then confirmation is shown And no command is dispatched before confirmation.
```

The authoring agent normalizes this into `IntentSpec`.

### 4.3 IntentSpec

`IntentSpec` preserves product meaning independently of component choices. It
contains:

- Stable requirement IDs
- Objective requirement kinds
- Exact domain data or action references
- Viewport policy
- Structured BDD scenarios
- Explicit assumptions

Separating intent from implementation lets the system re-plan against a new
catalog or theme without losing the reason the interface exists.

### 4.4 SurfaceSpec

`SurfaceSpec` records:

- Selected semantic components
- Selection rationale
- Typed data bindings
- Registered action bindings
- Requirement traceability
- Coarse layout recipe
- Platform capabilities

It does not contain arbitrary JSX, CSS, event handlers, or backend commands.

### 4.5 What the POC taught us about the language

Meaningful intent needs more than visible fields and action labels. The first
live generations required three reusable semantic concepts to be added to the
language:

- Collection filtering with an explicit field, operator, and value
- Multi-key collection ordering with explicit priority and direction
- Action absence, so “review-only” or “no actions” is an enforceable property
  rather than an omission the planner can accidentally reverse

These are domain-independent constraints. They belong in `IntentSpec`,
`SurfaceSpec`, and the compiler rather than in prompt exceptions. The same
principle should govern future language growth: add a primitive only when a real
intent cannot be expressed and objectively checked with existing ones.

### 4.6 Agent knowledge distribution

Surface must ship procedural agent knowledge as a first-class, versioned product
artifact. Types and component manifests tell an agent what is legal; a skill
teaches it how to choose well, preserve invariants, extend the language, and
verify the result.

The POC includes one project-local `building-surface-interfaces` skill with
progressively loaded authoring, architecture, and verification references. A
larger product may split this by audience:

- Authoring surfaces from intent
- Extending catalogs, domains, and adapters
- Operating Surface actions safely

Skills must version with the schema and catalog, point to those sources of
truth, and avoid duplicating machine-readable manifests where possible. Contract
tests remain authoritative when prose and behavior disagree.

A separate skill should not be required merely to read a public Surface page.
Semantic HTML and negotiated JSON or Markdown must remain useful to an agent
that has never heard of Surface. Skills improve authoring and operation; they do
not excuse a non-self-describing output format.

## 5. Component selection

Traditional low-level component APIs force an authoring agent to make too many
implementation choices. The first catalog should be task-oriented:

- `RecordDetail`
- `DataTable`
- `MetricGroup`
- `Alert`
- `Timeline`
- `DecisionPanel`

Future components may include `SearchResults`, `Comparison`, `Workflow`,
`Document`, `Artifact`, `Form`, and `JobStatus`.

Each component publishes a semantic signature:

```json
{
  "name": "DataTable",
  "purpose": "Compare and scan similarly shaped records",
  "fits": ["collection", "comparison", "high density"],
  "avoidWhen": ["image-first browsing", "long narrative"],
  "guarantees": ["native table HTML", "stable row identity"]
}
```

An authoring agent should retrieve components by data shape, task, density, and
constraints instead of relying on memorized names. Component manifests need
positive examples, counterexamples, allowed children, data schemas, action
affordances, projection behavior, and accessibility contracts.

The planning result should be explainable: component selected, reason,
alternatives, trade-offs, assumptions, and requirements satisfied.

## 6. Runtime architecture

```text
Natural-language intent
        ↓ structured model output
IntentSpec
        ↓ catalog-constrained planning
SurfaceSpec
        ↓ compiler ── failed report ──▶ one bounded repair turn
Bound semantic surface + ContractReport
        ├── React SSR → HTML/accessibility tree
        ├── AgentSnapshot → JSON
        ├── AgentSnapshot → Markdown
        └── Action registry → human and agent dispatch
```

The suggested eventual package boundaries are:

```text
@surface/schema       Canonical intent and UI language
@surface/catalog      Semantic component definitions and recipes
@surface/compiler     Validation, traces, and projections
@surface/react        React/SSR renderer
@surface/themes       Visual systems
@surface/actions      Typed command registry
@surface/web          HTML, JSON, and Markdown delivery
@surface/webmcp       Browser-agent adapter
@surface/author       Authoring tools/MCP server
@surface/test         Contracts and agent benchmarks
```

## 7. Agent consumption

### 7.1 Browser agents

Rendered pages use native semantic elements, explicit accessible names and
states, stable identity, visible disabled reasons, and meaningful action labels.
Visual hierarchy remains important because some agents are vision-first or
hybrid.

### 7.2 Search and URL-fetching agents

The default page is useful server-rendered HTML without JavaScript. Pages use
headings, articles, sections, definition lists, tables, lists, `time` elements,
citations, visible units, and text equivalents for non-text displays.

### 7.3 Alternate representations

Stable alternate resources are generated from the same bound surface:

```text
/refund/ref_2041
/refund/ref_2041.agent.json
/refund/ref_2041.md
```

The HTML and HTTP `Link` headers advertise these resources. JSON preserves raw
and displayed values. Markdown is a lossy reading projection and is never an
authoritative action representation.

Display formatting rendered during SSR must also be deterministic across server
and browser runtimes. Locale, calendar, and timezone are part of the semantic
contract, not ambient browser preferences. The POC uses a fixed English UTC date
representation; a production system should resolve an explicit formatting
context and serialize it with the bound surface.

Full duplicate JSON and Markdown should not be independently authored or blindly
embedded in every page. Dynamic browser snapshots and authenticated server
routes must observe the same access controls as HTML.

### 7.4 Operating agents

Operating agents need registered tools with schemas, availability, disabled
reasons, effect/risk hints, confirmation requirements, and structured results.
WebMCP is a promising optional adapter but, as of August 2026, remains a Draft
Community Group Report and Chrome origin trial rather than a W3C standard.

## 8. Executable UI contract

The compiler can guarantee declared objective properties, not subjective quality
in general. Verification is divided into three tiers.

### 8.1 Compile-time checks

- Intent and surface schema validity
- Component and action registration
- Data-path existence
- Action-input schema parity
- Stable unique identities
- Requirement trace coverage
- Semantic fit for requirement kind
- Collection filter and ordering policy
- Explicit action presence or absence
- Confirmation policy for destructive actions
- Responsive capability agreement
- Human/agent source-value parity

### 8.2 Runtime BDD scenarios

Structured scenarios use domain fixtures, one action, and objective expectations
such as:

- Confirmation becomes visible
- Command is not dispatched before confirmation
- Command is dispatched after the allowed transition
- Pending state appears
- Duplicate submission is prevented
- Unauthorized action is unavailable
- Disabled reason is exposed
- No action is exposed on a review-only surface

The scenario evaluator and React renderer share the same action policy. Browser
tests additionally exercise accessible controls and dialog behavior.

### 8.3 Evaluative checks

Human or model review can assess hierarchy, clarity, efficiency, tone, and
visual quality. Model judgments should initially be advisory, not hard build
gates. Screenshot-only assertions must not substitute for executed behavior.

### 8.4 Traceability

Every requirement receives a stable ID. Surface nodes declare which IDs they
implement, and the compiler verifies the node's actual semantics rather than
trusting the declaration. The output is a coverage matrix with concrete
evidence.

## 9. Proof-of-concept

### 9.1 Falsifiable hypotheses

1. Catalog-constrained planning yields valid, accessible UI more reliably than
   unconstrained JSX generation.
2. Intent requirements survive component selection and rendering.
3. BDD-style interaction requirements can be normalized and executed.
4. A second agent can recover facts and actions from generated HTML/JSON more
   accurately than from a conventional generated page.
5. One constrained theme produces consistent human quality across different
   intents.

### 9.2 POC scope

The first POC uses a refund-operations domain with fixed data, actions, and
behavior fixtures. This isolates UI planning from backend generation.

Included:

- Text intent authoring
- Structured `IntentSpec` generation
- Catalog-constrained `SurfaceSpec` generation
- Six semantic components
- Requirement traceability
- Static and BDD contract checks
- React SSR renderer and one theme
- Semantic HTML, JSON, and Markdown outputs
- Human/agent shared action bindings
- Explicit collection filter and sort semantics
- Explicit action-absence requirements
- One compiler-feedback repair turn when first-pass planning fails
- Side-by-side authoring workbench

Deferred:

- Screenshot and wireframe interpretation
- General data modeling and backend generation
- Production command execution and authorization
- Arbitrary custom components
- Drag-and-drop editing
- Multiple themes or renderers
- Runtime untrusted UI generation
- MCP Apps and WebMCP adapters

### 9.3 POC benchmark

Run fixed intent briefs through two paths:

1. Baseline prompt directly generating React and CSS
2. Surface pipeline generating IntentSpec and SurfaceSpec

Compare first-pass validity, repair turns, missing requirements, binding errors,
accessibility violations, action behavior, agent extraction accuracy, agent
action-selection accuracy, and visual consistency. A single attractive output is
not sufficient evidence.

The implemented development harness uses 12 public cases spanning information
hierarchy, history, queues, collection filters and ordering, action absence,
confirmation, permissions, responsive capability, and conversational wording.
Both pipelines receive the same human brief, domain, fixture data, and action
registry. Gold requirement, scenario, HTML, and action oracles remain outside
the generation prompts and are scored deterministically.

The direct-React lane must emit semantic action and capability metadata, then
runs in a scrubbed, time-bounded Node child process with filesystem permissions
limited to its generated bundle and with no network permission. This permits a
meaningful baseline without evaluating model-authored code in the main process.

The harness records one JSONL result per case, run, and pipeline, including
prompt version, model, Git revision, duration, token use, checks, generated
artifacts, and errors. A Markdown report keeps strict pass rate separate from
average scores so a safety failure cannot disappear inside an aggregate.

Evaluation layers:

1. **Intent recovery:** requirement recall and precision, plus scenario recall.
2. **Surface compilation:** contract pass, component fit, capability fidelity,
   action registry use, input binding, availability, and confirmation.
3. **Rendered semantics:** required and forbidden facts, collection order,
   native structure, agent summary, responsive capability metadata, and action
   metadata.
4. **Mutation sensitivity:** intentionally corrupt valid surfaces and require
   the compiler to reject every corruption, with zero safety-critical escapes.
5. **Optional consumption:** give an unfamiliar model only HTML, agent JSON, or
   Markdown and score answers to fixed fact and action questions.

No model judge is an authoritative gate. Human visual review can supplement the
objective suite, but does not replace executable semantic and safety checks. The
public set is a development suite and can be overfit; product claims require
repeated runs, model/version pinning, and a separately maintained unseen
holdout.

### 9.4 POC workbench

The workbench exposes:

- Original human intent
- Interpreted requirements and assumptions
- Selected components and rationales
- Human preview
- Contract coverage and scenario evidence
- Agent JSON
- Markdown
- Standalone fetchable HTML and alternate URLs

## 10. Security boundary

The surface action registry projects existing secure commands. It must not turn
arbitrary browser event handlers into trusted tools. Server execution always
reauthorizes and revalidates. Risk and confirmation metadata improve agent and
human affordances but are not authorization mechanisms.

No agent-only mutation should exist in an opted-in surface during the early
product phase. Every exposed mutation should have an equivalent human
affordance, and both should call the same dispatcher.

## 11. Success metrics

### Agent authoring

- First-pass schema validity
- Number of repair turns
- Tokens per accepted surface
- Hallucinated component/property rate
- Correct data/action bindings
- Precision of incremental edits

### Agent consumption

- Fact extraction accuracy
- Entity and relationship recovery
- Citation/source preservation
- Action selection accuracy
- Form and workflow completion
- Destructive-action error rate

### Human experience

- Accessibility conformance
- Task completion and time
- Responsive behavior
- Visual consistency
- Runtime performance
